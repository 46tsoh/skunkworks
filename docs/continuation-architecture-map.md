## 1. Strix — reverse-engineering map

### Core agent loop & orchestration

_Strix CORE agent loop & multi-agent orchestration (openai-agents SDK + LiteLLM)_

**Components**
- **run_strix_scan** (`/home/user/usestrix/strix/strix/core/runner.py`) — Top-level scan entrypoint/orchestrator. Resolves model via LiteLLM/StrixProvider, builds RunConfig (with SandboxRunConfig, tool_not_found_behavior='return_error_to_model'), creates/restores the AgentCoordinator, hydrates on-disk state (todos/notes/coverage/threat_models), connects MCP registry, builds the root agent + child factory, wires the spawn_child_agent closure into the shared context dict, opens the root SDK SQLiteSession, and calls run_agent_loop for the root. Handles resume (agents.json + agents.db), budget policy, and terminal exception mapping (BudgetExceeded/RateLimit/Cancelled -> status).
- **AgentCoordinator** (`/home/user/usestrix/strix/strix/core/agents.py`) — Single owner of all graph state: statuses, parent_of (the 'graph of agents'), names, metadata, per-agent AgentRuntime (SDK Session, asyncio.Task, live stream, mailbox, wake Event). Provides register/send/consume_pending/wait_for_message, status transitions, budget pause/resume/stop machinery (resume_epoch), parent-notice claiming, subtree cancellation, and JSON snapshotting to agents.json for resume. This is where routing of inter-agent messages and reachability decisions live.
- **run_agent_loop / _run_until_lifecycle / _run_cycle** (`/home/user/usestrix/strix/strix/core/execution.py`) — The driver. run_agent_loop runs the agent once (non-interactive) or forever parking on messages (interactive). _run_until_lifecycle drives the agent until a lifecycle tool settles its status, nudging text-only turns back into tool calls (bounded by recovery limit). _run_cycle calls Runner.run_streamed(agent,...), pumps stream_events to the event_sink, and handles recovery: image-rejection strip, context-overflow compaction, transient model-error retry w/ backoff, crash salvage, and budget pause/stop/reserve raises. spawn_child_agent + _start_child_runner create a child's session + detached asyncio.Task running its own run_agent_loop. respawn_subagents revives children on resume.
- **build_strix_agent / make_child_factory** (`/home/user/usestrix/strix/strix/agents/factory.py`) — Builds the openai-agents SandboxAgent (SDK Agent subclass) for root vs child. Assembles the tool list (_BASE_TOOLS + registered extras + finish_scan for root OR agent_finish for children + wait_for_user when interactive), wraps every FunctionTool for arg-coercion/result-bounding/strictness, adds Filesystem+Shell sandbox capabilities, and sets tool_use_behavior=_finish_tool_use_behavior so a run only ends when a lifecycle tool returns success (or a wait tool parks in interactive). make_child_factory closes over run-level config so the graph tool can spawn children without knowing runner internals.
- **render_system_prompt / _resolve_skills** (`/home/user/usestrix/strix/strix/agents/prompt.py`) — Jinja renderer for the system prompt (prompts/system_prompt.jinja + scope.jinja). _resolve_skills composes the ordered skill set per agent: requested skills + scan_modes/<mode> (+diff) + tooling + analysis + coordination/root_agent (root only) + whitebox skills. Shared skills are placed first as a cacheable prefix; per-run scope goes last (CACHE_POINT) for prompt caching.
- **agents_graph tools (create_agent, view_agent_graph, send_message_to_agent, wait_for_agents, agent_finish, stop_agent)** (`/home/user/usestrix/strix/strix/tools/agents_graph/tools.py`) — The model-facing orchestration tools. create_agent spawns a specialist child via the context's spawn_child_agent closure (validates skills, passes parent history as inherited context). wait_for_agents parks the agent until a peer/child message arrives. send_message_to_agent routes a message into another agent's mailbox. agent_finish is subagent termination -> posts a structured completion report (incl. authoritative filed report ids) to the parent's inbox and marks completed. stop_agent gracefully cancels an agent subtree. view_agent_graph renders the tree. These are where the model makes spawn/route/stop/finish decisions.
- **ReportUsageHooks** (`/home/user/usestrix/strix/strix/core/hooks.py`) — openai-agents RunHooks implementation attached to every run. on_llm_start increments the LLM turn counter, injects turn/budget wind-down warnings, and (pause policy) raises BudgetPausedError to park before a paid call. on_llm_end records SDK usage/cost and raises BudgetExceededError (stop), BudgetPausedError (interactive), or SubagentBudgetReservedError (90% reserve cutoff for sub-agents). This is where cost/turn-based stop/continue decisions are enforced.
- **sessions helpers** (`/home/user/usestrix/strix/strix/core/sessions.py`) — SQLiteSession wrapper (one agents.db row-space per agent_id) plus out-of-band write lock, seed_initial_input (persist opening task before first turn), replace_session_items (crash salvage), and image-budget/overflow scrubbing used by the recovery paths in _run_cycle.
- **inputs builders** (`/home/user/usestrix/strix/strix/core/inputs.py`) — Pure builders: build_root_task (renders targets/scope/user instructions into the root's first user message), build_scope_context/build_scan_targets (authorized targets for the prompt), make_model_settings (reasoning effort, tool_choice, prompt-cache injection points for LiteLLM/Claude), and child_initial_input (collapses inherited parent history + identity line + task into one user message for a spawned child).
- **finish_scan tool** (`/home/user/usestrix/strix/strix/tools/finish/tool.py`) — Root-only termination tool. Validates/persists the executive report (summary/methodology/technical analysis/recommendations) into report state, computes coverage summary + skill-coverage gaps from the agent graph, and returns scan_completed=True which _finish_tool_use_behavior recognizes to end the root run.

**Entry points**
- run_strix_scan() in core/runner.py — the whole scan starts here; called by the CLI/SaaS layer with scan_config, image, coordinator, interactive, max_turns, max_budget_usd, model.
- run_agent_loop() in core/execution.py — per-agent driver; called once for the root by the runner and once per child inside the detached _child_loop task.
- Runner.run_streamed(agent, input, run_config, context, max_turns, session, hooks) inside _run_cycle() — the actual openai-agents SDK tool-calling loop; Strix wraps one SDK streamed run per 'cycle'.
- create_agent tool (agents_graph/tools.py) — the model's entrypoint for spawning specialists; dispatches to the runner's spawn_child_agent closure -> core/execution.spawn_child_agent -> _start_child_runner.

**Decision points (decision-model targets)**
- ROUTE (inter-agent messaging): AgentCoordinator.send() in core/agents.py:425 decides deliverability — drops to unknown or terminal-non-resumable targets (returns False), appends to the target's mailbox, bumps pending_counts, and if the target has a live stream + interrupt_on_message set, cancels the stream (mode='immediate') to interrupt its current turn. _message_to_session_item (agents.py:609) formats user vs peer-agent messages. send_message_to_agent (agents_graph/tools.py:169) is the model-driven route; on failure it reports the target's status and tells the model to read list_reports instead of waiting.
- SPAWN: the model calls create_agent (agents_graph/tools.py:494); it validates skills (validate_requested_skills), snapshots ctx.turn_input as inherited parent_history when inherit_context=True, then calls the context 'spawn_child_agent' closure (runner.py:575) -> core/execution.spawn_child_agent (execution.py:389) which mints an 8-hex child_id, builds the child agent via the child factory, registers it in the coordinator with parent_id, and _start_child_runner opens its SQLiteSession and launches a detached asyncio.Task running run_agent_loop. Children run in parallel; the parent continues immediately.
- STOP vs CONTINUE vs FINISH (per turn): _run_until_lifecycle (execution.py:539) is the core arbiter. tool_use_behavior=_finish_tool_use_behavior (factory.py:600) makes a streamed run end ONLY when a lifecycle tool (finish_scan/agent_finish/finish_pr_review) returns success, or (interactive) when wait_for_user/wait_for_agents parks. A turn that ends with plain text leaves status 'running' and is nudged back into a tool call via _append_tool_required_message, bounded by _INTERACTIVE_TOOL_RECOVERY_LIMIT (3) or max_turns (non-interactive). Exhausting recovery: non-interactive -> crashed + MaxTurnsExceeded; interactive -> park as 'stalled' and notify parent.
- FINISH: root calls finish_scan (finish/tool.py) — root-only, persists the executive report + coverage gaps, returns scan_completed=True; subagent calls agent_finish (agents_graph/tools.py:609) — marks 'completed', renders a structured completion report with authoritative filed report ids, and posts it to the parent's mailbox (claim_parent_notice ensures exactly one parent notice).
- WAIT/PARK: wait_for_agents (agents_graph/tools.py:293) parks the agent (wait_kind='agents'); interactive agents park indefinitely and are woken by send(); non-interactive agents check active_agents_except(me) first (no point waiting if nobody is running) and block on wait_for_message with a timeout. _plain_waiting_timeout (execution.py:698) decides whether a parked agent is auto-resumed on a 300s timer (only wait_kind='agents', capped at _MAX_IDLE_AUTO_RESUMES=3).
- BUDGET stop/pause/reserve: enforced in ReportUsageHooks (core/hooks.py). on_llm_end raises BudgetExceededError (policy 'stop' -> coordinator.trigger_budget_stop wakes all agents to exit), BudgetPausedError (interactive or policy 'pause' -> park before next LLM call, resumed via coordinator.resume_budget with resume_epoch), or SubagentBudgetReservedError at 90% (_SUBAGENT_BUDGET_RESERVE) to cut sub-agents so the root can write its report. Warnings are injected at 70/85/95% bands in on_llm_start.
- RESUME (whole-scan restart): runner.py:341 — if agents.json exists, restore the coordinator, recompute budget flags, find root (parent=None), respawn_subagents (execution.py:454) revives non-terminal children as fresh tasks (start_parked if they weren't running), and a new --instruction is injected as a user message into root's session.
- RECOVERY routing inside a single SDK run: _run_cycle (execution.py:761) decides per-exception — image rejection -> strip images + retry (<=3), context overflow -> force compaction + retry (<=2), transient model/provider error -> exponential backoff retry (<=5), structured provider refusal -> fail, MaxTurnsExceeded -> stopped, UserError/AgentsException/APIError -> failed, else crashed; always salvages the crashed stream into the session and notifies the parent before unwinding.

**Extension points**
- register_agent_tools(*tools) in agents/factory.py:698 — register extra tools added to BOTH root and children (after base set, before the lifecycle tool); mirrored by strix.runtime.backends.register_backend. build_strix_agent also takes per-agent extra_tools.
- run_strix_scan kwargs: root_instructions_override / replace_root_scan_prompt (customize root prompt), extra_system_prompt_context, root_finish_tool and report_tool (swap the terminal/report tools — e.g. strix-pro's finish_pr_review), coverage_tools=False (drop coverage ledger), subagent_turn_limits (per-skill soft turn caps), event_sink / status_sink / mcp_status_sink (interface hooks), mcp_connection_requests (inject MCP connections from a SaaS caller instead of ~/.strix/mcp-servers.json).
- event_sink: StreamEventSink callback receives (agent_id, SDK stream event) for every streamed event — this is the hook a UI (TUI / run viewer) consumes to render live agent activity.
- Skills system: prompts/system_prompt.jinja + strix/skills/ drive agent specialization; _resolve_skills composes them and get_available_skills feeds the model its menu for create_agent.
- coordinator injection: run_strix_scan accepts an external AgentCoordinator, letting the caller observe/drive graph state, pause_budget/resume_budget, and snapshot for resume.

**Observations**
- Strix is built directly on the openai-agents SDK: agents are SandboxAgent (SDK Agent subclass with Filesystem+Shell sandbox capabilities), the loop is Runner.run_streamed, memory is the SDK's SQLiteSession (one agents.db, keyed per agent_id), and lifecycle/usage is RunHooks. LiteLLM is reached through StrixProvider/configure_sdk_* in strix.config.models; the SDK's own tool-calling loop drives tool execution.
- The 'graph of agents' is NOT an SDK handoff graph — it is Strix's own AgentCoordinator holding parent_of plus per-agent AgentRuntime (asyncio.Task + SDK Session + mailbox + wake Event). Each agent is an independent detached asyncio.Task running its own run_agent_loop; they run concurrently and communicate only via mailboxes the coordinator owns.
- One 'cycle' == one Runner.run_streamed call. _run_until_lifecycle loops cycles until a lifecycle tool settles status. Because tool_use_behavior only treats a successful lifecycle tool (or a parking wait tool) as final output, plain-text turns can never silently end a run — they are force-nudged back into tool calls. This is the central mechanism keeping an autonomous scan running 'until it finishes'.
- Interactive vs non-interactive is the big behavioral switch. Non-interactive (autonomous): run once, agents die on terminal status and are unreachable, wait_for_agents is bounded, recovery exhaustion -> crash. Interactive: run_agent_loop parks forever on wait_for_message, any agent (incl. completed) can be woken by a message, errors park instead of killing the runner (_run_cycle_parked), and resume is supported. A perpetual/autonomous 'run until done' corresponds to non-interactive mode with finish_scan as the only clean exit.
- State is fully persisted for resume: coordinator JSON -> agents.json (statuses, parent_of, mailboxes, budget flags, recovery/idle counts) via _maybe_snapshot after every mutation; SDK conversation -> agents.db; plus hydrated todos/notes/coverage/threat-model ledgers. respawn_subagents rebuilds the live task graph from these on resume.
- Message delivery can interrupt a running turn: coordinator.send cancels the target's live SDK stream (mode='immediate') when interrupt_on_message is set (interactive), so a new instruction is seen on the next cycle; stop_agent uses mode='after_turn' so the current turn completes and saves first.
- Budget control is layered: soft turn warnings, per-role cost warning bands (root 70/85/95, sub-agent 75/80/85), a 90% sub-agent reserve that stops children so the root can still write its report, and two policies — 'stop' (warn then hard-stop at limit) vs 'pause' (silent park-before-next-call, resumable with a raised limit via resume_epoch).
- Child context is inheritance-by-value: create_agent snapshots the parent's turn_input (images scrubbed) into the child's single opening user message as 'background only'; children do not share the parent's live session. Results flow back up only through agent_finish completion reports (which carry authoritative filed report ids read from report state, not the model's prose) landing in the parent mailbox.

**Decision points (decision-model targets)**
- LLM DEDUP JUDGE (the single explicit LLM-as-judge decision) — /home/user/usestrix/strix/strix/report/dedupe.py:check_duplicate(). Called by create_vulnerability_report._do_create before persisting. Flow: (1) short-circuit returns not-duplicate if no existing reports; (2) _check_dependency_duplicate() is DETERMINISTIC (no LLM) — matches on CVE + package_name + ecosystem + manifest_path identity; (3) otherwise an LLM is invoked with DEDUPE_SYSTEM_PROMPT ('expert vulnerability report deduplication judge') comparing the candidate against _prepare_report_for_comparison-cleaned existing reports (fields: title, description, impact, target, technical_analysis, poc_description, endpoint, method, cve, dependency_metadata; values truncated to 8000 chars). Model = dedupe.model (STRIX_DEDUPE_MODEL) or falls back to settings.llm.model. Returns strict JSON {is_duplicate, duplicate_id, confidence 0-1, reason}; _parse_dedupe_response + _validate_duplicate_reference enforce the id refers to a real report. FAIL-OPEN: any exception or empty response returns is_duplicate=false (never blocks a finding on a dedupe error). Caller rejects the new report when is_duplicate true.
- DEDUP MODEL ISOLATION — /home/user/usestrix/strix/strix/report/dedupe.py:resolve_dedupe_model() + _dedupe_model_settings(). STRIX_DEDUPE_REASONING_EFFORT sets its effort. tools=[], output_schema=None, tracing DISABLED. Usage recorded under agent_id='dedupe'.
- SEVERITY / CVSS TRIAGE is NOT an LLM decision — it is DETERMINISTIC. /home/user/usestrix/strix/strix/tools/reporting/tool.py:_calculate_cvss() builds a CVSS:3.1 vector from the agent-supplied 8-metric cvss_breakdown and computes score+severity via the `cvss` library (CVSS3.scores()/severities()), mapping 'none'->'info'. The LLM's judgment enters only by CHOOSING the 8 metric letters; the band is computed. Extensive prose guidance in the create_vulnerability_report docstring steers that choice (CVSS calibration rules, C/I/A gating, don't-presuppose-separate-compromise, reserve H for demonstrated broad impact).

**Decision points (decision-model targets)**
- Dispatcher start (raptor.py:_get_or_start_dispatcher): lazy, one per invocation. On start failure, _dispatcher_failure_reason is recorded and the run falls back to env-direct SDK calls (dispatcher-down resilience) — never breaks the run, but loses per-run budget scoping + L5 audit.
- Worker credential posture (raptor.py:_run_script + dispatcher/spawn.py): RAPTOR_LLM_WORKER_KEYLESS=1 → child gets get_safe_env() (keyless, relies on dispatcher injection); default → get_llm_env() carries provider keys as an env-direct fallback. spawn_worker with env=None falls back to get_safe_env(preserve_proxy=True), not an empty env.
- Dispatcher plane selection (dispatcher/server.py): trusted same-UID RAPTOR processes use the full-capability worker socket (renewable tokens, /_child/* management); credential-proxy sandboxes must bridge to child_socket_path (scoped child tokens only, non-renewable, no renewal/management). Worker plane is never bridged.
- Token lifetime (server.py L4): worker tokens renew TTL in place while live (bounds time-since-last-renewal, a stranded token still dies within one TTL); scoped child tokens are non-renewable (short TTL sized by the minting caller). In-process self-serve route uses a 7-day TTL since the token dies with the process anyway.
- Bedrock auth mode (dispatcher/auth.py): AWS_BEARER_TOKEN_BEDROCK bearer token takes precedence over SigV4 (matching AWS SDKs); SigV4 needs parent-only botocore. No usable auth/region → 503 provider not configured. Mantle vs Runtime surface selected by the URL prefix the worker addresses.
- Model routing tier (dispatch/broker/hints.py): require (hard pin, fail if unavailable) vs prefer (try first, broker may override on failure) vs defer (broker decides from task shape + scorecard). exclude_models prevents fallback collision; max_cost_usd caps per-call spend; SpeedTier trades latency/cost.
- Scorecard short-circuit (llm/config.py): a 'trusted' (low measured miss-rate) cell short-circuits the fast tier, but scorecard_shadow_rate (default 5%) still runs full ANALYSE to keep fresh ground-truth flowing for drift detection. scorecard_enabled=False runs the full path always.
- Agentic enrichment gating (agentic_passes.py): each pass is skipped (with a skipped_reason, base pipeline continues) when claude not on PATH, block_cc_dispatch=True (untrusted target repo), lifecycle start fails, or the subprocess fails. Functions never raise.
- Validate-postpass finding selection (agentic_passes.run_validate_postpass): only findings with is_exploitable==True OR confidence=='high' are persisted (to a file, defending against finding_id prompt injection) and handed to /validate; the understand sibling is auto-discovered by the bridge.
- Gap priority tiering (audit/gaps.py): entry-point(-1) > no-tool-coverage(0) > partial(1) > stale(2) > fully-covered(3) > dead-code(4). Stale (source hash changed since review) re-enters as a gap carrying its old annotation. LLM gap_ranking can only reorder WITHIN a tier, never across — so budget truncation can't drop a mechanically-protected gap.
- Tool-coverage gate resolution (audit/tool_coverage.py): CWE covered by ≥1 available tool AND that tool is silent → clean/disconfirmed; CWE not in the map / no covering tool → dark (fails conservative, routes to human/LLM review). dark_verify classes withhold the semgrep silence→clean channel so witness execution stays primary.
- Evidence shedding under budget (audit/evidence_grade.py): HIGH-confidence evidence is never shed from the prompt; LOW is shed first. Source tag separates mechanical (verifiable/deterministic) from llm (probabilistic) from dynamic evidence; a finding's confidence = its strongest evidence.
- Hypothesis seeds are hints not verdicts (audit/hypothesis_intake.py): a seed can boost gap priority and add a prompt hint but can never mint/suppress a finding or resolve a function — the LLM still forms the hypothesis, tools still render the verdict. Seeds naming unknown functions are recorded as misses, not errors.
- Oracle reliability class (orchestration/driver.py): 'decisive' (deterministic, trusted unsupervised) vs 'judgement' (LLM-based, requires downstream validation). The driver treats it as metadata for the caller, not a branch it acts on itself.
- Budget enforcement gate (llm/client.py): dispatch is refused when _effective_spent (max of client total_cost and provider_spend_usd, so neither surface is missed and failed-attempt spend still counts) + estimated_cost exceeds effective cap (max_cost_per_scan minus any held reserve). Non-finite ledger fails CLOSED (returns inf) rather than silently disabling the cap via NaN comparisons.
- Non-dollar governor (llm/config.py): because max_cost_per_scan is inert for free/local models and inf for audit runs, independent max_seconds/max_calls/max_tokens_per_scan caps gate at the same provider chokepoint regardless of enable_cost_tracking — the only backstop against a runaway local/looping run (None = that dimension unlimited).
- Funnel verdict bucketing (orchestration/funnel.py): is_true_positive True → true_positive, False → false_positive (and severity_mismatch when scanner level=='error'), any other value (notably None from a q<0.5 empty cc_dispatch) → unverdicted — fixing the prior bug that counted None as a confirmed finding. Self-contradictory findings are excluded from exploitable and counted as inconsistent.
- Audit loop driver (audit/orchestrator.py): the same context/record/sweep/gaps modules run whether the Python orchestrator drives the loop autonomously or the human+Claude skill path does — only the loop driver differs, so autonomous and interactive audits are behaviourally equivalent.

**Observations**
- Three cleanly layered dispatch tiers: core.llm.providers (call a named model) → core.dispatch.broker (pick the best model for a task shape) → future scheduler. Consumers bind to the layer that matches their needs.
- Credential isolation is the dispatcher's whole reason to exist: parent holds keys in an in-memory CredentialStore (keys read-and-erased from env at construction), workers reach a UDS and the dispatcher injects the real auth header. 5 defence layers (fs 0700/0600, peer-UID check, FD-passed capability token, budget+TTL+revocation, JSONL audit). Tokens go via inherited FD specifically because same-UID processes can read /proc/N/environ.
- The audit engine is hypothesis-driven and tool-grounded: LLM forms a hypothesis (claim + disproof recipe), hypothesis_mapping turns it into a mechanical check (coccinelle/semgrep/smt), tools render the verdict, and evidence_matches_hypothesis tests whether returned evidence actually confirms/refutes — the LLM proposes, the tools dispose.
- Coverage tracking is central: a function is reviewed only if it's a 'gap' (no coverage record / finding / checked_by label); staleness via source-hash. The review journal (post-2026-07-28) is the SOLE verdict authority; the .audit-log.jsonl is telemetry only. Gates resolve to 'clean' only when a covering tool is available and silent; otherwise 'dark' (conservative, needs review).
- Budget model is defence-in-depth and fails closed: dollar cap gates on max(client ledger, provider ledger) so failed-attempt spend still counts; non-finite ledgers refuse further dispatch; a held reserve guarantees late-phase headroom; and a separate non-dollar governor (seconds/calls/tokens) backstops free/local runs where the dollar cap is inert or inf. Model scorecard lets trusted cells short-circuit the fast tier while a 5% shadow rate keeps drift detection alive.
- Everything degrades gracefully rather than crashing: dispatcher-down → env-direct fallback; claude-not-on-PATH or untrusted repo → agentic passes skip with a reason; junk hypothesis seeds → 'no seeds'; the base pipeline always continues.
- packages/autonomous is fuzzing support (crash prioritisation, cross-campaign memory, multi-turn crash dialogue, corpus gen, exploit validation) driven by the operator's duration timer in raptor_fuzzing.py — it is NOT the audit review loop and deliberately has no autonomous stop-condition.
- Untrusted-input discipline is pervasive: hypothesis seeds, gap fields, and context injections are bounded, schema-validated, escaped-at-load and length-capped; finding selection for /validate is persisted to a file to defend against finding_id prompt injection; the bash launcher sweeps hostile env functions and scrubs PATH before running any external command.

**Observations**
- The staged /validate chain is a strict division of labor: Stage 0 (Python inventory + capability preflight) and Stage E (Python binary feasibility, via the exploit_feasibility engine) bracket LLM-driven stages A (discovery), B (attack trees/hypotheses/evidence), C (sanity vs real code), D (ruling), F (self-review). - The architectural spine is 'mechanical evidence floors LLM opinion'. - Two distinct 'validation' subsystems exist and are complementary, not redundant: (1) exploitability_validation = the staged source->binary PIPELINE for scanner/agentic findings; (2) hypothesis_validation = a tight LLM<->mechanical-tool LOOP for testing individual hypotheses. hypothesis_validation.posterior adds a calibrated Bayesian layer that the audit orchestrator uses for chain-outcome scoring.

Per-adapter weights (CodeQL dataflow >> Semgrep pattern) are the documented tuning surface.
- The labeled corpus is a measurement instrument, not production data: 155 finding/label pairs with ground-truth TP/FP verdicts and a closed 6-category FP taxonomy (missing_sanitizer_model, infeasible_branch, framework_mitigation, dead_code, type_constraint, reflection_imprecision). **Principles**
- [emil-design-eng] Taste is trained, not innate; unseen details compound (Paul Graham's 'thousand barely audible voices'); beauty is leverage because people pick tools on overall experience.
- [emil-design-eng] Animation decision framework, in order: (1) Should it animate at all? Never animate keyboard-initiated or 100+/day actions (Raycast has no palette animation); (2) Name the purpose (feedback, spatial consistency, state indication, preventing jarring change, explanation) or don't build it; (3) Easing: ease-out for enter/exit, ease-in-out for on-screen movement, ease for hover/color, linear for constant motion, NEVER ease-in on UI; (4) Duration: UI stays under 300ms (press 100-160ms, tooltips 125-200ms, dropdowns 150-250ms, modals/drawers 200-500ms).
- [emil-design-eng] Use strong CUSTOM easing curves, not weak built-ins: --ease-out cubic-bezier(0.23,1,0.32,1), --ease-in-out cubic-bezier(0.77,0,0.175,1), --ease-drawer cubic-bezier(0.32,0.72,0,1).
- [emil-design-eng] Component craft: buttons scale(0.97) on :active; NEVER animate from scale(0) (start 0.9-0.97 + opacity:0); popovers are origin-aware (transform-origin at trigger, modals exempt/stay centered); tooltips skip delay+animation on subsequent hovers; use CSS transitions (not keyframes) for rapidly-triggered UI so they retarget; use filter: blur(<20px) to mask imperfect crossfades; animate enter with @starting-style.
- [emil-design-eng] Springs (simulate physics, no fixed duration) for drag momentum, 'alive' elements, interruptible gestures, decorative mouse-tracking; Apple-style { duration, bounce 0.1-0.3 } is easier to reason about than mass/stiffness/damping; springs carry velocity through interruption, CSS/keyframes restart from zero.
- [emil-design-eng] Performance: animate ONLY transform and opacity (GPU, skip layout/paint); don't drive a child's transform via a parent CSS variable (recalcs all children); CSS animations run off main thread and beat JS/rAF under load; use WAAPI for programmatic CSS-performance animation; Motion hardware-accelerates x/y/scale only on 14.2+.
- [emil-design-eng] Accessibility: prefers-reduced-motion means fewer/gentler (keep opacity/color, drop movement), not zero; gate hover motion behind @media (hover: hover) and (pointer: fine) to avoid false taps.
- [emil-design-eng] The Sonner principles for loved components: DX is key (drop-in, no hooks/context); good defaults beat options; naming creates identity; handle edge cases invisibly; transitions not keyframes for dynamic UI; build an interactive docs site. Plus: match motion to the component's personality (cohesion); review animations the next day in slow motion; asymmetric timing (slow when the user decides, fast when the system responds); stagger entrances 30-80ms.
- [sibling: animate] Build sequence is a gate that may correctly produce zero lines of code; pick the cheapest tool that works (CSS transition -> @starting-style -> CSS animation -> WAAPI -> Motion); if the task is really a component (toast/drawer/menu) stop and use pick-ui-library; reduced-motion and hover-gating ship WITH the animation, never as a follow-up; extend the codebase's existing tokens, don't fork them; never present motion as a menu of options.
- [sibling: choreograph] Good choreography is mostly cutting moving parts and running the rest in parallel; one entrance per container (if the panel slides in, its items are just there); sequence only when order carries meaning (reading order, cause/effect, physical arrival); uniform stagger is forbidden (reads like a metronome) — vary by importance; cast every element as Lead/Support/Decoration/Static; relationships are Together/Overlap/Sequence/Carry; choreography never blocks interaction; every sequence must survive mid-flight interruption; exits are simultaneous, shorter, simpler, and match the entry path.
- [sibling: apple-design] Interfaces feel alive when motion starts from the current on-screen value, inherits the user's velocity, projects momentum forward, and can be grabbed/reversed at any instant; kill latency (respond on pointer-down, feedback continuous during the gesture); 1:1 direct manipulation respecting grab offset via setPointerCapture; interruptibility is the single most important principle (animate from presentation value, blend velocity, never lock out input); think in damping ratio + response not mass/stiffness/damping (default damping 1.0, add bounce ~0.8 only when the gesture carried momentum); velocity handoff and momentum projection (exponential-decay, not v^2/2a); translucent materials convey depth/hierarchy (backdrop-filter, never stack two light translucent surfaces); size-specific tracking (tighten large text ~-0.02em, body near 0) and inverse leading; the eight foundations — Purpose, Agency, Responsibility, Familiarity, Flexibility, Simplicity (not minimalism), Craft, Delight.
- [sibling: pick-ui-library] Curated, taste-driven picks (only runs when explicitly invoked): base-ui (unstyled accessible primitives), cmdk (command menus), Sonner (toasts), input-otp (OTP), motion/Framer Motion (springs/layout/exit), NumberFlow (animating numbers), recharts (general charts) / Liveline (streaming charts), dnd kit (drag and drop), Virtuoso (virtualization), zustand (state), clsx + cva (className/variants), next-themes (dark mode no flash). Identify the task not the named library; check package.json first; recommend one, don't present a menu.
- [sibling: find-animation-opportunities] Read-only, restraint-first (premise: 'You Don't Need Animations'); every candidate must pass a 4-question gate (Frequency, Purpose, Speed, Function) in order; cap output at 5-7 per app; a REQUIRED 'rejected candidates' section (with the gate question that killed each) is what separates it from an animation wishlist; never modifies source.
- [design-taste-frontend] Build the website a good company would ship: say plainly what is sold, show the real thing on every screen, look made-for-this-client (not a template, not an art piece); figma.com and x.ai are the bar.
- [design-taste-frontend] Nine house rules that win over everything else: (1) no caption/description under any image — credits in one footer line; (2) every visual renders at 1440/1024/768/390, never an empty ground; (3) one section per screen (hero alone first, each section 1-2 screens, no second heading peeking in; exception: a live photo-chapters section); (4) equal left/right content edges; (5) hover micro-animations (card lifts 2px, photo zooms 1.02-1.03, buttons step/press, underlines draw, loops cycle 2.5-4s) plus a hero entrance and one or two 'dealt moments' per page — never stripped; (6) more and better real photographs; (7) real full-colour icons (never drawn look-alikes) and small diagram visuals; (8) big award-site scenes/shader effects ONLY on technical subjects (tech/AI/dev-tools/gaming/fintech/hardware), never on a cafe/bakery/shop (those get photographs); (9) address/contact rules — district only, no house number/postcode/phone, contacts on .example.
- [design-taste-frontend] The kind of business decides everything: declare page type on <html data-type> and metas; six kinds — software, gaming, tech/hardware (product), product, service, place — each with its own page plan, allowed assets, and section order. Effects, scenes, loops, counts, CSS grounds, dark pages/heroes are 'tech only'; 'other' kinds get photographs, flat colour, type, real icons, hero entrance, one dealt moment, hover layer.
- [design-taste-frontend] Deal, never choose by taste: dedicated scripts deal the hero, palette, type pairing, radius, and moments with a saved history so pages differ; take the first palette/pairing printed; NEVER violet/lavender in the page's own design; a physical product with no photos is shown in listed stand-in photographs (a 3D render only when the brief asks).
- [design-taste-frontend] Write all copy first within strict rules: h1 names category + buyer/place, one hard fact on the first screen, a noun in every heading, buttons as verb + object, 60-80 words a screen on tech; invent nothing except a searched coined brand name and (on a place) plausible hours/prices marked data-assumed; a 'voice of its own', no slop words / stock phrases (copy-lint enforces this).
- [design-taste-frontend] Enforcement is non-negotiable: a Stop-hook finish gate (gate.mjs) runs the checker at 1440 and 390, walks 320 for overflow/collide/tap-size, and runs copy-lint; every FAIL blocks; fix until GATE: PASS or GATE: OPEN (3 rounds max). Never edit the kit's own files or hide anything from the checker to clear a check; a genuinely false FAIL is waived in waivers.json with its reason. A large checklist covers first screen, one-section-per-screen, equal edges, every-visual-draws, no-caption, right-things-for-the-kind, motion, contacts, keyboard/head/a11y, one design system, copy/links, perf, and responsive at 820/768/390/320.

**When to use:** emil-design-eng: whenever building or reviewing UI where polish matters — animations, transitions, component feel (buttons, popovers, tooltips, toasts, drawers), gestures/drag, perceived performance, or when something 'feels off'. ## 4. Unified architecture (target design)

**Unified architecture**

AEGIS — one orchestrator, two engines, one decision layer, one knowledge base, one UI. The design makes Strix's dynamic-testing "graph of agents" and RAPTOR's static/hypothesis audit two peer engines under a single AgentCoordinator, both writing to one shared knowledge base and routing every judgment through the existing reference/jev DecisionRouter.

SUBSYSTEMS:
(1) Orchestration — a Strix-style AgentCoordinator owns all graph state (statuses, parent_of, per-agent runtime = task + session + mailbox + wake event, budget flags, resume snapshots to agents.json). RAPTOR's static audit is modeled as ONE specialist agent subtree ("static-audit" agent) spawned into the same graph as the Strix dynamic agents; it internally runs the RAPTOR review-sweep-record / staged /validate loop but communicates results only through the KB and mailbox completion reports, exactly like any Strix subagent. A perpetual "run-until-finished" driver (non-interactive mode, finish_scan the only clean exit) loops cycles until all engine agents settle, with graceful resume.
(2) Tool/scanner adapters — a single adapters layer wraps Strix's dynamic tools (shell/exec_command, agent-browser, Caido proxy, MCP client) and RAPTOR's static tools (Semgrep, CodeQL, SCA, fuzzers, Coccinelle/SMT) behind a uniform adapter contract that emits the one findings model.
(3) Unified findings / knowledge base — one Finding/Hypothesis/Evidence/Coverage/ThreatModel/Report model (superset of Strix report fields + RAPTOR final_status tiers + Bayesian posterior/strength + evidence chain + tri-axis status) persisted in a resumable KB that both engines read and write. Coverage ("negative space") and the shared threat model carry across engines.
(4) Decision layer — reference/jev promoted to a first-class package. ONE DecisionRouter instance shared by both engines, with per-kind namespaced thresholds (strix.* and raptor.*), JSONL decision log, caching, and record_outcome calibration fed by RAPTOR's labeled corpus. Backends: BasalOmniBackend (self-hosted, default for sensitive targets), JevBackend, LLMJudgeBackend (wraps each framework's existing LLM), StaticBackend (offline/deterministic). Core principle preserved from both upstreams: the router is ADVISORY on LLM-judgment decisions; mechanical floors (deterministic CVSS, RAPTOR's verdict ladder, Stage E capability ceiling, provenance stamps, fail-open dedupe, fail-closed budget) always override the router and can never be laundered by it.
(5) Reporting — one deterministic (no-LLM) report builder feeding exports (SARIF, CSV with injection hardening, CycloneDX SBOM, encrypted PDF, run.json) and the UI from the same KB artifacts; preserves RAPTOR's tri-axis model (scanner level vs security severity vs exploitability verdict) and Strix's executive narrative + coverage gaps.
(6) UI — a single React/Tailwind web app served from one JSON+WebSocket contract off the KB (replacing Strix's 500ms polling with revisioned delta sync borrowed from the Strix TUI projection), redesigned to impeccable Operate-mode standards with a real design-token system.

PERPETUAL RUN + ULTRACODE: the orchestrator runs non-interactive until every agent reaches terminal status (dynamic agents via finish_scan/agent_finish, the static-audit agent when its gap queue is exhausted and all confirmed findings have passed /validate), auto-resuming from the KB snapshot on any crash, and governed by both Strix budget hooks (warn/pause/stop/reserve) and RAPTOR's non-dollar governors (max_seconds/calls/tokens) so a free/local model cannot run away. The continuation CLI session should be launched with maximum reasoning ("ultrathink"/ultracode) and the loop skill so it keeps resuming the same run until the finish condition is met. This replaces any need for a human in the loop between cycles while preserving the defensive boundary (sample/benign data and user-authorized targets only).

**Module layout**

- `aegis/` — New top-level unified framework package (name = AEGIS). Everything new lives here; reference/jev and poc/ are extended and kept, not replaced.
- `aegis/findings/` — The single findings/knowledge model. Extends poc/models.py Candidate/ReportFinding into Finding (Strix report fields + CVSS breakdown), Hypothesis+Evidence (RAPTOR), Coverage, ThreatModel, Report, and a final_status tier enum (exploitable>likely_exploitable>confirmed_constrained>confirmed_blocked>confirmed_unverified>ruled_out) with canonical snake_case normalization (RAPTOR core/status).
- `aegis/decision/` — Promote reference/jev to first-class. Re-exports DecisionRouter/DecisionClient/backends; adds calibration.py (corpus replay + per-kind precision/recall + threshold recommendation using RAPTOR-style labeled corpus) and thresholds.yaml (strix.* / raptor.* per-kind config).
- `aegis/kb/` — Shared knowledge base: findings store, coverage ledger (one-row-per-surface, evidence-required outcomes), threat model (required sections, keyed by normalized target identity), notes/todos, run journal (sole verdict authority), and resumable JSON snapshots. Both engines' single source of truth.
- `aegis/orchestrator/` — Strix-style AgentCoordinator (graph state, mailboxes, budget pause/resume/stop, snapshot/resume), the per-agent run loop driver (cycle = one streamed run; lifecycle-tool-ends-run; plain-text turns nudged back to tool calls), the perpetual run-until-finished driver, and the spawn closure that launches both dynamic agents and the static-audit agent.
- `aegis/engines/dynamic/` — Strix replication: SandboxAgent-style agent + factory, prompt/skill resolution (frontmatter+jinja skills, external-dir shadowing), agents_graph tools (create_agent/send_message/wait/finish/stop), reporting/coverage/threat_model/notes/todo tools, output_store spill, budget RunHooks.
- `aegis/engines/static/` — RAPTOR replication: gaps (priority tiers + staleness), hypothesis_intake (seeds as hints-not-verdicts), hypothesis_mapping (claim->cocci/semgrep/smt), evidence_grade, tool_coverage (CWE->tools, dark-by-default), the staged /validate orchestrator (Stage 0/A-F with mechanical floors + capability preflight + Stage E ceiling), and the Bayesian posterior (Beta-Bernoulli) engine.
- `aegis/adapters/` — Uniform tool/scanner adapters emitting the one findings model: semgrep.py, codeql.py, sca.py, fuzzing.py (static/RAPTOR); shell.py, agent_browser.py, proxy_caido.py, mcp.py (dynamic/Strix). SARIF/finding-stream merge + cross-engine dedup on (file,line,vuln_type).
- `aegis/reporting/` — Deterministic report builder + renderers (markdown/json/html/sarif/csv/cyclonedx/pdf), coverage map, funnel bucketing (TP/FP/unverdicted/inconsistent/exploitable), corpus precision/recall/F1. CSV formula-injection + markdown-fence escaping preserved.

**Interop strategy**

ONE FINDINGS MODEL: a single Finding type is the lingua franca. It is the superset of Strix's vulnerability report (title/description/impact/CVSS 8-metric breakdown/CWE/CVE/code_locations/PoC/http_exchange_ids/counterevidence) and RAPTOR's audit output (final_status tier, Bayesian posterior + strength, graded evidence chain with EvidenceSource, coverage linkage). It carries the tri-axis cleanly: scanner level (error/warning/note) vs security severity (deterministic CVSS band) vs exploitability verdict (RAPTOR tier). Both engines construct the same object; the KB stores exactly one row per deduped vulnerability.

ONE DECISION ROUTER: a single DecisionRouter instance is injected into both engines. Decision kinds are namespaced (strix.triage.true_positive, strix.dedupe.same_vuln, strix.route.next_agent, raptor.validate.sanity, raptor.validate.ruling, raptor.hypothesis.posterior, …) with per-kind thresholds in thresholds.yaml. One decisions.jsonl captures the whole combined run for replay/calibration; record_outcome feeds the labeled corpus back to tune thresholds. Fail-open (dedupe) and fail-closed (budget) semantics are per-kind, not global.

ONE ORCHESTRATOR: the AgentCoordinator graph holds Strix dynamic agents and a RAPTOR static-audit agent as peers. Interop is cross-feeding through the KB, not a merged loop: (a) the static engine's hypotheses/findings are written as hypothesis seeds that boost the dynamic agents' triage priority and as prompt hints (RAPTOR's hypothesis_intake "hints-not-verdicts" contract — a seed can never mint/suppress a finding); (b) the dynamic engine's confirmed, reachable findings are handed to the static /validate chain as candidates for mechanical exploitability grading; (c) both reconcile against the shared coverage ledger so neither re-reviews a surface the other closed. Dedup across engines runs on (file,line,vuln_type) with a semantic dedupe gate (router) on collision; a dataflow-path-carrying row supersedes a path-less one (RAPTOR's merge rule).

ONE KNOWLEDGE BASE + ONE CONTRACT: findings, coverage, threat model, notes, journal and resume snapshots live in aegis/kb and are the only thing the reporting layer and the UI server read. That shared contract (run.json / findings.json / transcript shapes) is what lets a single UI render both engines without either engine knowing the UI exists.

**Decision-layer integration**

reference/jev plugs into each mapped decision_point as an ADVISORY router call where the decision is LLM-judgment, while mechanical gates stay mechanical and override it. Wiring, by framework:

STRIX decision points ->
- ROUTE (AgentCoordinator.send / send_message_to_agent target choice) -> router.choose("strix.route.next_agent", ...). Deliverability (terminal/unknown target) stays mechanical.
- SPAWN (create_agent: is a specialist worth spawning + which skills) -> router.gate("strix.spawn.worthwhile") + router.choose("strix.spawn.skills"); skill validation stays mechanical.
- STOP vs CONTINUE vs FINISH (_run_until_lifecycle arbiter) -> router.choose("strix.lifecycle.next"); the tool_use_behavior rule (only a successful lifecycle tool ends a run) stays mechanical, so the router can never silently end a run.
- WAIT/PARK and auto-resume timer -> router.gate("strix.wait.should_park").
- DEDUPE (report/dedupe.check_duplicate) -> router.gate("strix.dedupe.same_vuln"); FAIL-OPEN preserved (any error => not duplicate), dependency-CVE identity stays deterministic (CVE+package+ecosystem+manifest).
- TRIAGE / when-to-file -> router.gate("strix.triage.true_positive") (low threshold, errs toward keeping).
- CVSS -> the router may propose each of the 8 metric letters via choose, but the score+band is ALWAYS computed deterministically by the CVSS library (never an LLM scorer).
- COVERAGE outcome classification (reported/ruled_out/needs_follow_up) -> router.choose("strix.coverage.outcome").
- CONTEXT COMPACTION (what to keep) -> router.score / choose; budget stop/pause/reserve stays in RunHooks (fail-closed), router only logs it.

RAPTOR decision points ->
- Stage A IRIS tier-1 mechanical refute -> stays mechanical; router.gate("raptor.validate.stageA_keep") only where judgment is needed.
- Stage B reachability demotion / SMT path feasibility -> SMT sat/unsat stays mechanical; router.score("raptor.path.proximity") only for the soft judgment band.
- Stage C sanity check vs real code -> router.gate("raptor.validate.sanity"); a finding without a passing sanity check is mechanically capped at confirmed_unverified.
- Stage D RULING (confirmed / ruled_out / confirmed_unverified) -> router.choose("raptor.validate.ruling"), but the mechanical downgrade ladder and terminal-status skip set floor it.
- Stage E feasibility verdict mapping + capability preflight -> verdict->final_status map and the no-binary ceiling stay deterministic; router.gate("raptor.capability.go") turns the warning-only preflight into an informed pre-spend go/no-go.
- HYPOTHESIS posterior -> router.score("raptor.hypothesis.posterior", 0..1) feeding the Beta-Bernoulli posterior; the verdict_from mechanical ladder (tool failure->inconclusive; confirmed-claim-no-matches->refuted) is never overridden by the router.
- MODEL ROUTING broker (require/prefer/defer) -> router.choose("raptor.broker.model").
- GAP_RANKING listwise reorder -> router.choose, constrained to within one mechanical priority tier (cannot cross tiers).
- CVSS_LINT + CORPUS pivot gate -> router consumes the warning stream as calibration features; record_outcome against the corpus drives threshold tuning (the "future hard gate" the code anticipates).

Pattern throughout: the router removes scattered ad-hoc model calls and makes every branch typed, logged, cached, threshold-tuned and unit-testable — the exact engineering win the POC already demonstrates — without weakening either framework's "mechanical evidence floors LLM opinion" invariant.

**Risks**

- Scope drift past the defensive boundary: replicating an autonomous pentest agent graph risks producing attack capability. Mitigate by replicating only orchestration/UI/reporting, running on sample/benign data and user-authorized targets, and bundling no weaponized exploit content.
- License/attribution: Strix is Apache-2.0, RAPTOR is MIT. Reimplementing patterns is fine; copying code beyond license terms is not. Strix is built on the openai-agents SDK — reusing vs reimplementing that loop is a licensing + maintenance decision.
- Two renderer stacks drift (Strix already maintains a Go TUI and a React web UI by hand). Mitigate with the single aegis/server data contract and one tokenized status/severity source so any second surface renders from the same spec.
- Perpetual-run cost/compute runaway, especially with a free/local model where the dollar cap is inert. Mitigate with RAPTOR's non-dollar governors (seconds/calls/tokens) plus Strix budget hooks (pause/stop/reserve), both fail-closed.
- Over-trusting the decision router could weaken each framework's 'mechanical evidence floors LLM opinion' invariant. Mitigate by keeping CVSS computation, the RAPTOR verdict ladder, Stage E ceiling, provenance stamps and fail-open dedupe strictly mechanical and able to override the router.
- Prompt injection from untrusted target-derived text (findings, hypotheses, transcripts). Mitigate by preserving RAPTOR's neutralize/escape/bounded-read discipline and Strix's output_store bounding, and by treating all KB-ingested target text as data.
- Jev/basal-omni exact wire formats are unverified; the UI 954KB eager bundle and 500ms polling are known perf traps the overhaul must actually fix, not reproduce.

**Guardrails**

- Defensive scope only: operate on sample/benign data and explicitly user-authorized targets; replicate framework/orchestration/UI/reporting, never new attack capability.
- No weaponized exploit content bundled; the staged /validate and exploitability reasoning run over finding text and authorized targets, not shipped exploits.
- Mechanical floors are inviolable: deterministic CVSS, RAPTOR verdict ladder, Stage E capability ceiling, provenance/witness stamps, fail-open dedupe, fail-closed budget — the decision router is advisory and cannot launder an unverified finding into a higher tier.
- Untrusted-content discipline: bound, schema-validate and escape all target-derived text at ingest; terminal/UI output sanitized against ANSI/control/bidi hijack; hypothesis seeds are hints, never verdicts.
- Credential isolation preserved (RAPTOR dispatcher pattern): analysis subprocesses never hold API keys; keys injected at a proxy chokepoint.
- Budget defense-in-depth always on in perpetual mode (dollar cap + non-dollar governors), fails closed on a non-finite ledger.
- License + attribution: reimplement Strix (Apache-2.0) and RAPTOR (MIT) patterns in original code, keep NOTICE/attribution, copy no code beyond license terms.

**Gaps to close**

- gh/GitHub auth is currently BROKEN (GH_TOKEN invalid) — an autonomous session's commit-and-PR loop will fail at `gh pr create`. The prompt (or the harness launching it) must either supply a valid token or explicitly tell the session to fall back to local commit + branch push and log the blocker instead of retrying forever.
- Upstream Strix and RAPTOR source code is NOT present in the repo — only a research/design note describes them. 'Totally replicate' is therefore only achievable as pattern reimplementation. If true fidelity is wanted the prompt must authorize a read-only clone of the upstreams (with licensing care); otherwise it must explicitly scope the work to reimplementation and forbid inventing upstream internals.
- No explicit, numeric finish condition or soak-time/governor cap is defined anywhere concrete — the perpetual loop has no agreed terminal state or runaway ceiling. This must be pinned in the prompt or the loop cannot safely terminate.
- The 'user-authorized target' mechanism is undefined — there is no place in the KB that records consent, and no sample authorized target. For a defensive build over sample data this can be resolved by restricting to in-repo sample data only, but the prompt must say so.
- Scanner tooling (semgrep/codeql) and pytest are absent with uncertain install path behind the proxy; without committed offline SARIF/finding fixtures, M2 and M7 have no verifiable green bar.
- The 8-milestone scope is very large for one unattended run; realistically the session may not reach M8. There is no stated fallback for 'ran out of budget at M4' — the prompt must guarantee each milestone is independently shippable so a partial run is still a clean, mergeable deliverable.
- 'ultracode' is not a recognized mode/tool in this harness; its intended meaning must be resolved (ultrathink + loop skill is the best available interpretation).
- Jev and basal-omni request/response wire formats are unverified (isolated as constants in decision_client.py); which backend is the default for unified runs is unstated. Defaulting to StaticBackend for all verifiable runs sidesteps this but must be declared.

**Risks**

- Scope drift past the defensive boundary: 'fully replicate an autonomous pentest agent graph with a browser/proxy/sandbox' edges toward real attack capability. Highest-severity risk. Contain to orchestration/UI/reporting over in-repo sample data; no real-host reach; /validate reasons over text only.
- Perpetual-loop compute/cost runaway, especially with a free/local model where any dollar cap is inert — must be bounded by fail-closed non-dollar governors (seconds/calls/tokens/cycles) and a precise finish condition, or it spins indefinitely.
- The impeccable UI gate loop never converging — an unattended session chasing a perfect audit/critique score can loop forever; needs hard per-screen iteration caps and numeric 'good enough' thresholds.
- Half-built, non-shippable intermediate state if the run dies mid-milestone; mitigated only if each milestone is committed independently-green (tests pass + golden invariant intact).
- Hallucinating upstream Strix/RAPTOR internals because the source isn't in the repo — produces plausible-but-wrong 'replication'. Mitigate by scoping to documented patterns and recording assumptions.
- Branch/PR mishandling: stacking commits on a merged or stale branch, or looping on failed `gh pr create` due to the invalid token; mitigate with explicit restart-from-main steps and an auth pre-check.
- Over-trusting the DecisionRouter and 'refactoring' the mechanical floors (CVSS, verdict ladder, Stage-E ceiling, fail-open dedupe) into router calls, weakening both frameworks' core invariant.
- Adding third-party dependencies (React/Vite, semgrep) may fail or be non-deterministic behind the restricted proxy, breaking the offline-reproducible guarantee the current codebase relies on; keep core stdlib-only and isolate heavy deps.
- Prompt injection from untrusted target-derived text ingested into the KB/UI if ingest isn't bounded/escaped.
